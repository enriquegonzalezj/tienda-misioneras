# Tienda en línea y donativos: Misioneras Hijas de la Purísima Virgen María

## Qué es este proyecto
- Tienda en línea de Vocaciones MHPVM (merch, papelería, accesorios y artículos religiosos) con módulo de donativos, para una congregación en Aguascalientes, México. Arranca con pocos productos y debe soportar al menos 100 sin cambios. Quienes la administran no son técnicas.
- Lo desarrolla Enrique (Madrid) con Claude Code, en Windows 11 con PowerShell o Git Bash. Es su primer proyecto real con Claude Code: necesita entender cada paso, no solo aprobarlo.
- Fechas: entrega oficial acordada con la congregación el jueves 19 de noviembre de 2026. El cronograma interno es solo ilustrativo: no se recorta ni se simplifica trabajo por las fechas (Enrique prefiere entregar tarde que incompleto).
- Las tareas tienen un ID (1.3, 4.6, 6.1...) que viene del cronograma interno de Enrique. Úsalo cuando él lo mencione.

- Frontend: React 18 + Vite 7 + Tailwind CSS 4. JavaScript, no TypeScript. Tailwind se conecta con el plugin `@tailwindcss/vite`; no hay `tailwind.config.js` ni `postcss.config.js` (el tema se define en CSS con `@theme`, ver Diseño). `package.json` lleva `"type": "module"`.

En `public/` (Vite lo copia tal cual a `dist/`) está `og-imagen.jpg`, la imagen por defecto al compartir (1200 × 630, logo blanco sobre `#0C3F68`); si cambia el logo, se rehace.
- El panel tiene sus propias carpetas: `pages/admin/` (`AdminLayout`, `AdminLogin`, `Inventory`, `Categories`, `ProductForm`, `Shipping`) y `components/admin/` (`AdminNav`, `FormField`, `StatusDot`, `InventoryProduct`, `SaveBar`, `Toggle`, `ProductDetails`, `ProductSidebar`, `ProductOptions`, `ProductVariants`, `ProductPhotos`). Las funciones de cada pantalla están en `api/catalog.js`, `api/auth.js`, `api/admin.js`, `api/cart.js`, `api/checkout.js` y `api/orders.js`.
- Backend: Flask + SQLAlchemy, migraciones con Flask-Migrate. Archivos en `src/api/`: `models.py`, `routes.py`, `catalog.py` (API pública), `cart.py` (carrito), `reservations.py` (liberar reservas vencidas), `checkout.py` (pedido y consulta por token), `auth.py`, `passwords.py`, `limiter.py`, `slugs.py` (direcciones únicas), `commands.py`, `sample_data.py`, `seo.py` (lo que Flask pone en cada página, robots y sitemap; ver SEO), y los del panel: `admin_catalog.py`, `admin_products.py`, `product_form.py`, `admin_images.py`, `images.py` y `admin_shipping.py`. En local, el servidor escucha solo en localhost y la app se conecta con un usuario propio que es dueño de la base, nunca con el superusuario postgres.
- **Flask sirve también el frontend** (`serve_frontend` en `src/app.py`). No hay sitio estático separado. En cada página, Flask entrega el `index.html` con título, descripción, Open Graph y, en la ficha, precio y datos estructurados ya puestos (SEO y vista previa al compartir por WhatsApp o redes), con el código HTTP correcto. Después React funciona como SPA. **Las rutas públicas de `page_for` (`seo.py`) y las de `routes.jsx` deben coincidir**: al crear una pantalla nueva (`/donaciones`, `/cuenta`, `/aviso-de-privacidad`...), se agrega en los dos. Ver SEO.

Límite de intentos con Flask-Limiter 4.1, en memoria. El código vive en `src/api/auth.py` (sesión, decoradores y rutas `/api/auth`), `passwords.py` (hash y reglas) y `limiter.py`. Ver Seguridad.

- Imágenes: Cloudinary (SDK `cloudinary`), con Pillow 13 en el servidor para revisarlas y limpiarlas antes de subir (ver Seguridad). Si falta `CLOUDINARY_URL` o la carpeta no es válida, la app arranca igual y subir una foto responde 503.
- Hosting: Render (un servicio web para Flask más frontend, y PostgreSQL de pago).
- Python con pipenv (`Pipfile` y `Pipfile.lock`, ambos en el repositorio). Instalar paquetes siempre con `pipenv install <paquete>`, nunca con pip directo. ## Reglas de negocio
- Solo se venden productos físicos a direcciones de México. Los donativos están abiertos a cualquier país. Moneda: MXN.
- **Compra como invitada o con cuenta.** La compra sin registro siempre está disponible. Al final del pago se ofrece crear una cuenta con los mismos datos, más una contraseña. Con cuenta, la clienta ve su historial de pedidos y tiene sus datos guardados (una sola dirección). Incluye recuperación de contraseña por correo. La cuenta pide "Nombre(s)" y "Apellidos" en dos campos y teléfono opcional de 10 dígitos (uso permitido: entregas y avisos del pedido; usarlo para promociones exige declararlo en el aviso de privacidad con opción de negarse). La invitada consulta su pedido con un enlace que lleva un `access_token`.
- **Campañas de descuento.** No hay descuento automático por registrarse. La administradora crea campañas desde el panel con: público ("Solo clientas con cuenta", por defecto, o "Todas"), alcance (toda la tienda o productos seleccionados), porcentaje entero opcional y precios fijos opcionales por variante, fechas de inicio y fin (días completos en hora de México, ambos incluidos) y un interruptor "¿descuenta también el envío?" (apagado por defecto). En cada variante se cobra el precio más bajo entre el normal, el del porcentaje y el fijo; nunca se suman. Siempre se muestra el precio normal tachado. Dos campañas pueden coincidir en fechas solo si no comparten productos (una de toda la tienda los comparte todos): lo bloquea el panel y, si aun así coinciden, el servidor aplica el precio más bajo. Si dos descuentan el envío, se aplica el descuento mayor. Nunca aplican a donativos. Se calculan siempre en el servidor.
- **Existencias.** Se llevan por variante. Al público solo se muestra "disponible" o "agotado", nunca la cantidad. Un producto se muestra agotado cuando todas sus variantes lo están; una variante agotada aparece tachada y no se puede elegir. Se reservan al ir a pagar: el servidor crea el pedido pendiente y descuenta las existencias con las filas de las variantes bloqueadas (`FOR UPDATE`, siguiendo el orden de bloqueo de Envíos y reservas). Si no alcanza, ese pedido no se crea y se avisa a la clienta con un mensaje que no dice cuántas quedan ("No hay suficientes unidades"). La ficha y el carrito dejan pedir de 1 a 99 por variante: el 99 es solo un tope contra errores de dedo; la comprobación real la hace el servidor. La reserva dura 30 minutos (`reserved_until`), con el mismo límite en la preferencia de Mercado Pago; si la clienta genera una ficha de OXXO, se alarga hasta que vence la ficha (3 días). Al vencer sin pago, el pedido se cancela y las unidades vuelven. Las reservas vencidas se liberan cuando alguien consulta existencias o va a pagar (sin tareas programadas en Render). Ver Envíos y reservas.
- Envío: paqueterías con tarifa fija, guardadas en la base y editables en el panel (`/admin/envios`). Las tarifas las define y captura la congregación: nunca las inventes ni las pongas en el código o en variables de entorno. Sin ninguna paquetería activa no se puede pagar.
- Estados de pedido: pendiente, pagado, enviado, entregado y cancelado. Estados de donativo: pendiente, pagado y cancelado. El folio visible (MHP-000123) se calcula con el id y no se guarda.
- Donativos: monto libre (cada persona escribe cuánto quiere donar, sin montos sugeridos), con la misma pasarela que los productos pero en un flujo aparte del carrito, sin envío ni campañas. Valida en el servidor un monto mínimo mayor que cero. Se piden nombre completo y correo; ni país ni dirección. La interfaz no dice nada sobre deducibilidad ni facturación.
- Correos automáticos: confirmación a la clienta al confirmarse el pago, aviso de pedido o donativo nuevo a la congregación y recuperación de contraseña.
- Producto: nombre, slug, descripción, descripción corta para Google, categoría, imágenes (con texto alternativo obligatorio) y al menos una variante. Las categorías tienen dos niveles (categoría y subcategoría); si una categoría tiene subcategorías, el producto va obligatoriamente en una de ellas. Una categoría solo se borra si está vacía. El producto nace oculto hasta que la administradora lo activa. El slug se genera al crear, es editable, no se regenera al renombrar y lleva `-2` si se repite.
- **Variantes.** Todo producto tiene al menos una variante; un producto sin opciones tiene una sola variante por defecto. Máximo 2 opciones por producto (por ejemplo Color y Talla), con sus valores en orden (M, G, EG) y color de muestra opcional. Cada variante lleva SKU (texto único que escribe la administradora), sus valores de opción, precio de venta, costo de compra y existencias. El carrito, los pedidos y las existencias apuntan siempre a la variante, nunca al producto. En la ficha, si las variantes tienen precios distintos, el catálogo muestra "Desde" con el menor.
- **Vender nunca borra nada.** En el panel, un producto está visible (activo y con al menos una variante activa, lo mismo que la tienda), oculto (inactivo, o activo sin variantes activas) o archivado (`archived_at` con fecha: siempre oculto, lo exige un CHECK; sale de la vista normal del Inventario y conserva sus ventas). Desarchivar lo devuelve como oculto, para revisarlo antes de mostrarlo. Al público, una variante activa sin existencias sale agotada. "Borrar" un producto solo funciona si nunca se vendió; con ventas responde 409 y pide archivarlo, que es un botón aparte. Una variante con ventas no se puede quitar del formulario: se desactiva. La base lo garantiza: los renglones de pedido apuntan a la variante con RESTRICT, y una campaña usada en pedidos no se borra, se desactiva.
- Panel de administración, Etapa 1: productos con sus variantes, categorías y subcategorías (crear, editar y borrar si están vacías), imágenes, existencias por variante, pedidos, donativos y campañas.
- Panel de administración, Etapa 2: calculadora de precio (precio = costo / (1 - margen deseado)), margen real por variante descontando la comisión de Mercado Pago y los descuentos, tasa de IVA configurable, dashboard de ventas, costo y margen por periodo, e informes descargables en Excel (openpyxl).
- Toda la interfaz va en español de México. Variables, funciones y archivos, en inglés.
- **Textos sin género.** Lo que lee la persona (interfaz, mensajes de la API, correos y terminal) no marca género, porque también compran hombres y puede haber administradores: "Te damos la bienvenida", "Tu cuenta", "Cuenta de administración". En este documento se habla de clientas y administradoras solo por comodidad.

## Modelo de datos (tarea 1.3, en `src/api/models.py`)
- Catálogo: `categories` (dos niveles con `parent_id`; `card_text` e `image_public_id` opcionales para las tarjetas de Inicio), `products` (`is_active`, `is_featured`, `archived_at`), `product_images` (`alt_text` obligatorio, 150 caracteres como máximo), `product_options`, `product_option_values` (`position`, `swatch_hex`), `product_variants` y `variant_option_values`.
- Cuentas: `users` (un solo modelo con `role` `admin` o `customer`; el registro público siempre pone `customer`; las cuentas de administración se crean solo con `flask create-admin`), `addresses` (una por usuaria; `delivery_references` porque `references` es palabra reservada) y `password_reset_tokens` (enlaces de recuperación: solo el hash SHA-256 del token, `expires_at` y `used_at`).
- Ventas: `campaigns`, `campaign_variants` (`fixed_price` opcional), `shipping_methods` (paqueterías: `name` único, `price`, `delivery_time` opcional, `is_active`, `position`), `orders`, `order_items` y `donations`.
- `orders.shipping_method_id` apunta a la paquetería con RESTRICT: una paquetería usada en pedidos no se borra, se apaga. `orders.cancel_reason` dice por qué se canceló ("Reserva vencida", "Reemplazado por un pedido nuevo"). Índice `ix_orders_status_reserved_until` para buscar reservas vencidas.
- El pedido guarda una copia de los datos de la compradora, la dirección, el envío (nombre y precio de la paquetería, no el plazo) y, por renglón, nombre, precio normal (`list_unit_price`), precio cobrado (`unit_price`) y costo (`unit_cost`, para el margen de la Etapa 2). Si después cambia el producto, el pedido no cambia.
- Cada renglón guarda la campaña que le puso el precio (`order_items.campaign_id`; vacío si se cobró el precio normal, y la base exige campaña si el precio está rebajado). El pedido guarda la campaña que descontó el envío (`orders.shipping_campaign_id`).
- Mercado Pago: `mp_payment_id` único (webhook idempotente), `mp_status` y `mp_fee` (comisión real).
- `access_token` largo y aleatorio en pedidos y donativos, para que nadie vea uno ajeno cambiando el número.
- Convenciones: dinero en `Numeric(10,2)`, nunca Float. Fechas con zona horaria, en UTC. Estados como texto con CHECK, no ENUM nativo. Teléfono (10 dígitos) y código postal (5) como texto, validados por CHECK. Correos en minúsculas (CHECK; pasarlos a minúsculas en el servidor antes de guardar o buscar). `TimestampMixin` para `created_at` y `updated_at`. `NAMING_CONVENTION` en la metadata. `Base(DeclarativeBase)` con `SQLAlchemy(model_class=Base)`.
- Migraciones: `pipenv run migrate -m "mensaje corto sin acentos"` (va al nombre del archivo, que Alembic recorta a 40 caracteres). Revisa siempre el archivo generado antes de `pipenv run upgrade`. Alembic no detecta las restricciones CHECK nuevas en tablas que ya existen ni los renombres de columnas (los genera como borrar y crear): esos cambios se revisan y completan a mano en la migración. Los `batch_alter_table` vienen del `env.py` de la plantilla y en PostgreSQL no afectan.

## API pública del catálogo (tarea 3.2, en `src/api/catalog.py`)
- `GET /api/categories`: `total_products` y árbol `categories` con `name`, `slug`, `card_text`, `image` (`url` y `alt`, o `null`), `product_count` (la categoría madre suma las de sus subcategorías) y `children` (`name`, `slug`, `product_count`). Las categorías sin productos visibles no salen.
- `GET /api/products`: filtros opcionales `category` (incluye sus subcategorías), `featured=true`, `limit` (1 a 24, 12 por defecto) y `offset`; fuera de rango, 400; categoría inexistente, 404. Responde `total` e `items` con `name`, `slug`, `image`, `subtitle` (texto de la tarjeta: `card_subtitle` si está lleno, si no se calcula con las variantes, por ejemplo "2 colores · 3 tallas"), `price_min` y `sale_price_min` como texto (`"15.00"`), `price_varies` y `available`. Más recientes primero. `sale_price_min` queda en `null` hasta las campañas (4.8).
- `GET /api/products/<slug>` (tarea 3.4): `name`, `slug`, `subtitle` (frase bajo el nombre), `description` (texto plano: una línea en blanco separa párrafos; nunca HTML), `available`, `category` (`name`, `slug`; la más específica), `parent_category` (`name`, `slug`, o `null`), `images` (`url` de 1200 px, `thumb_url` de 240 px y `alt`, en su orden), `options` (`name` y `values` con `value` y `swatch_hex`, en su orden; solo valores que usa alguna variante) y `variants` (`values` en el orden de las opciones, por ejemplo `["Beige", "G"]`, `price` y `sale_price` como texto, `available`). Solo salen las variantes activas con un valor por cada opción. El mismo 404 "Producto no encontrado" si no existe, está oculto o no tiene variantes completas. Cada variante lleva su `id`: es el único id público y el carrito apunta a la variante con él (tarea 4.1). Nunca SKU.
- Visible = producto activo con al menos una variante activa. Nunca devuelve `cost`, existencias, SKU, ids internos (salvo el `id` de variante) ni productos ocultos. La URL de la imagen la arma el servidor (Cloudinary, `f_auto,q_auto`, ancho fijo).
- Inicio muestra los 4 destacados más recientes (`is_featured`, lo marca la administradora); sin destacados, la sección se oculta. Sin foto, las tarjetas muestran `ImagePlaceholder` (logo en gris tenue). Hasta que haya fotos oficiales de producto no se sube ninguna.

## Carrito (tarea 4.1)
- **Navegador (`cart/CartContext.jsx`).** `CartProvider` (lo pone `Layout`) y `useCart()` con `items`, `count`, `addItem`, `setQuantity`, `removeItems` y `clear`. Guarda en `localStorage` (`mhpvm-carrito`) solo `[{ variant_id, quantity }]`, nunca precios, nombres ni disponibilidad. Al leer valida: ids enteros positivos, cantidad de 1 a 99 (más se recorta), repetidas juntas y 50 líneas como mucho (los mismos límites que `cart.py`); lo que venga mal se descarta. Todo con try/catch: sin `localStorage`, funciona en memoria. Se sincroniza entre pestañas con el evento `storage`. `addItem` suma con tope 99 y responde `added`, `capped`, `full`, `too_many_lines` o `invalid` para el aviso de la ficha.
- **Cabecera.** El número es la suma de las cantidades del navegador (decisión de Enrique, 7 nov): sin petición en cada página. Lo agotado cuenta hasta que se quita; lo que el servidor manda en `removed` se quita solo al abrir `/carrito`. Más de 99 se ve "99+"; el número va en `aria-label` ("Carrito, 3 artículos").
- **Servidor (`POST /api/cart`, `cart.py`).** Recibe `{"items": [{"variant_id", "quantity"}]}`: máximo 50 líneas, cantidad 1 a 99, ids enteros positivos (no bool ni texto); repetidas se juntan con tope 99; formato malo, 400. Responde `items` (en el orden recibido: `variant_id`, `quantity`, `name`, `slug`, `values` como `[{option, value}]`, `image` con `url` de 240 px y `alt` o `null`, `price`, `sale_price` en `null` hasta la 4.8, `available` y `line_total`, `null` si está agotada), `removed` (ids inexistentes, de producto inactivo o archivado, o de variante inactiva o incompleta), `subtotal` (solo lo disponible) y `count`. Límite 120 por minuto por IP. No escribe en la base ni dice existencias.
- **Envío y total en `POST /api/cart` (tarea 4.2).** Acepta además `shipping_method_id` opcional (entero positivo; texto, bool, 0 o un número enorme: 400 "La paquetería no tiene un formato válido"). Responde también `shipping` (`id`, `name`, `price`, o `null`), `shipping_unavailable` (`true` si se mandó una paquetería que no existe o está apagada) y `total` (subtotal de lo disponible más el precio de la paquetería, o `null`). Es el mismo cálculo que `POST /api/checkout`: `/pago` muestra ese `total` y lo manda como `expected_total`, así el navegador nunca suma importes. `cart.py` no importa de `checkout.py` (al revés sí; lo contrario sería circular).
- **Ficha.** "Agregar al carrito" suma la cantidad elegida a la variante elegida (desactivado si está agotada); la cantidad no vuelve a 1. Aviso en un `role="status"` que siempre existe, con enlace "Ver carrito"; se limpia al cambiar de variante.
- **Página `/carrito` (`pages/Cart.jsx` y `components/CartLine.jsx`).** Sin maqueta; diseño aprobado por Enrique el 7 nov. Escritorio: líneas a la izquierda y resumen fijo a la derecha (`surface-alt`); móvil: resumen debajo. Cada cambio del carrito pide `POST /api/cart`; al cambiar cantidades, 300 ms después de la última pulsación y cancelando la petición anterior. Mientras recalcula, totales atenuados y `aria-busy`. Lo de `removed` se quita solo con aviso ("Quitamos 1 producto que ya no está disponible."). Lo agotado se queda con "Agotado", sin total y fuera del subtotal (decisión de Enrique, 7 nov). "Quitar" avisa y devuelve el foco al h1. Con error, aviso con "Reintentar" (si ya había datos, subtotal "Sin calcular"). "Continuar al pago" es un enlace a `/pago`; mientras carga, recalcula, falla o no hay nada disponible, es un botón desactivado (un enlace no se puede desactivar).
- **Cuándo se vacía.** Crear el pedido no vacía el carrito. Al confirmarse el pago (4.6) se quitan del carrito **solo las variantes pagadas**: lo agotado no entró en el pedido y se queda.

## Envíos y reservas (tarea 4.5)
- **Paqueterías (`admin_shipping.py`, pantalla `/admin/envios`).** Cada una: nombre (único; el panel lo compara sin importar mayúsculas), precio (0 = gratis, validado con `parse_cost`), plazo estimado opcional (vacío = no se muestra; en `/pago` sale como "Entrega estimada: ..."), activa o no, y orden con flechas. Arriba, un aviso si no queda ninguna activa ("por ahora no se pueden recibir pedidos"). En local hay dos "(provisional)" de `seed-sample`; en Render no hay valores inventados: las captura la congregación (nombres y tarifas reales pendientes de la 4.3).
- **Orden de bloqueo (regla).** Cuando un proceso bloquea filas, primero pedidos y después variantes, de menor a mayor id. Lo siguen `reservations.py`, `check_stock_changes` (`product_form.py`) y `checkout.py`; el webhook de Mercado Pago (4.6) debe seguirlo también. Así dos procesos a la vez nunca se esperan el uno al otro para siempre.
- **Liberar reservas (`reservations.py`).** `release_expired_reservations()` busca pedidos `pending` con `reserved_until` vencido (`FOR UPDATE SKIP LOCKED`, lotes de 50), devuelve las unidades sumando en la base (`stock = stock + n`, no en Python), pone `cancel_reason` "Reserva vencida" (`EXPIRED_REASON`), todo en una transacción. Si la base falla, lo anota en el registro y sigue (devuelve 0). Se llama antes de leer existencias en `GET /api/products`, `GET /api/products/<slug>`, `POST /api/cart`, la ficha de `seo.py`, el Inventario, `GET` y `PUT /api/admin/products/<id>`, `PATCH /api/admin/variants`, `POST /api/checkout` y `GET /api/orders/<token>`. Una ruta nueva que lea o cambie existencias también la llama.
- **Formulario de producto (`previous_stock`).** Las existencias de una variante solo se escriben si se cambiaron (`stock` distinto de `previous_stock`). Si además cambiaron en la base mientras se editaba, 409 sin guardar nada, error bajo el campo ("Ahora hay 14. Cambió mientras editabas.") y `stock_conflicts` para el reintento. ## SEO (tareas 3.5 y 5.7, en `src/app.py` y `src/api/seo.py`)
- URLs con slug (`/producto/playera-modelo-3`), generado a partir del nombre. Las variantes no tienen URL propia. Cada página pública lleva un solo h1 y texto alternativo en las imágenes. Imágenes de Cloudinary con `f_auto,q_auto` y carga diferida.
- **Entrega (`serve_frontend`).** Si la dirección es un archivo de `dist/`, se entrega tal cual (`safe_join` impide salir de `dist/`), salvo `index.html`, que siempre pasa por `seo.py`. Si no, `index.html` con el bloque entre `<!-- seo:inicio -->` y `<!-- seo:fin -->` cambiado y el código HTTP que decide `page_for`. La barra final da lo mismo. HTML con `Cache-Control: no-cache`. Sin `dist/`, 503 "Falta compilar el frontend". Una dirección `/api/...` inexistente responde 404 en JSON y un método equivocado 405 en JSON (`handle_not_found`, `handle_method_not_allowed`), nunca el HTML de la tienda.

En `NO_REFERRER_PREFIXES` (`pedido`) va además `Referrer-Policy: no-referrer`, para que el token de la dirección no salga en la cabecera `Referer` hacia otros sitios.
- **Títulos.** Inicio: "Tienda Vocaciones MHPVM"; el resto: "<página> | Vocaciones MHPVM" (también "Página no encontrada" y "Panel de administración"). El formato está en dos sitios: `_title` de `seo.py` (al entrar por una dirección) y `hooks/usePageTitle.js` (al navegar dentro de React). Si cambia uno, se cambia el otro. `usePageTitle(undefined)` no cambia nada mientras llegan los datos; lo usan `Home` (`""`), `Shop`, `Product` y `NotFound`. El panel no lo usa.
- **Descripción.** `seo_description`; si está vacía, el subtítulo o la descripción (producto) o `card_text` (categoría); si no, un texto general. Una línea, máximo 155 caracteres sin partir palabras.
- **Open Graph.** `og:site_name`, `og:locale` `es_MX`, `og:type` (`product` en la ficha), título, descripción, `og:url`, `og:image` con su alt (la primera foto en JPG, `f_jpg`, de 1200 px; sin foto o si Cloudinary falla, `/og-imagen.jpg` de 1200 × 630), y en la ficha `product:price:amount` (precio mínimo), `product:price:currency` `MXN` y `product:availability`; `twitter:card`. `canonical` y `og:url` salen de `PUBLIC_BASE_URL`, nunca de la petición. Con campañas (4.8), revisar qué precio se publica aquí y en el JSON-LD.
- **Datos estructurados (JSON-LD), solo en la ficha.** `Product` con `name`, `url`, `brand` Vocaciones MHPVM, `description` si hay, `image` solo con fotos del producto (nunca el logo) y una `Offer` por cada precio distinto (`InStock` si alguna variante con ese precio tiene existencias; `NewCondition`). No `AggregateOffer`: Google la reserva para varias tiendas. Nunca SKU, existencias ni costo.
- **`/robots.txt`** (blueprint `seo`): `User-agent: *`, `Allow: /` y `Sitemap: <PUBLIC_BASE_URL>/sitemap.xml`. No bloquea nada a propósito: bloquear `/admin` impediría que Google vea su `noindex`, y Google necesita `/api` para dibujar la ficha.

## Seguridad (obligatorio)
- Nunca escribas llaves ni contraseñas en el código. Nunca leas, muestres ni subas `.env`. Antes del primer commit, confirma que `.gitignore` lo excluye.
- Precios, descuentos, envío y totales se calculan siempre en el servidor, desde la base de datos. Nunca confíes en importes que mande el navegador.
- **El costo de compra es solo interno.** `cost` de la variante y `unit_cost` del renglón nunca aparecen en endpoints ni respuestas públicas, solo en las del panel.
- Pedidos y donativos de invitada se consultan solo con su `access_token` (generado con `secrets`), nunca con el id. El pedido va en la dirección (`/pedido/<token>`, 256 bits) con `noindex` y `no-referrer`; su respuesta nunca lleva SKU, costo ni ids.
- **Checkout.** Precios, envío y total salen del servidor: el total que ve la clienta y el `expected_total` salen del mismo cálculo (`POST /api/cart`) y `POST /api/checkout` lo vuelve a calcular con las filas bloqueadas. Límites contra acaparar existencias (ver Checkout y pedido). En `localStorage` solo el carrito (ids y cantidades) y el token del pedido pendiente, validados al leer; nunca datos personales.
- Webhook de Mercado Pago: verifica la firma según la documentación oficial vigente, consulta el pago a la API antes de marcar un pedido como pagado y hazlo idempotente.
- No toques ni registres datos de tarjeta.
- **Rutas protegidas.** Las del panel llevan `@admin_required` y las de cliente `@customer_required` (de `api/auth.py`). Las de cliente devuelven solo datos de `current_user`, nunca los de un id que llegue en la URL.
- **Sesión.** Cookie httpOnly, `Secure` en producción (`JWT_COOKIE_SECURE=false` solo en local) y `SameSite=Lax`. CSRF de doble envío: en POST, PUT, PATCH y DELETE el frontend copia la cookie `csrf_access_token` en la cabecera `X-CSRF-TOKEN`. Dura 1 h y se renueva sola mientras se usa. Cada petición busca la cuenta en la base: desactivarla o cambiar su contraseña cierra todas sus sesiones.
- **Contraseñas.** Mínimo 15 caracteres en cuentas de administración y 10 en clientes; máximo 128; sin reglas de mayúsculas ni símbolos. Se rechazan secuencias de teclado, la parte del correo antes de la arroba y el nombre de la tienda (`passwords.py`). El login da el mismo mensaje si el correo no existe, la contraseña falla o la cuenta está desactivada.
- **Límite de intentos.** Login: 5 fallidos por correo y 20 por IP cada 15 min (los correctos no cuentan). Registro: 20 por hora por IP. Pedir enlace de recuperación: 3 por hora por correo y 10 por IP. En Render, el límite por IP depende de `ProxyFix` (ya está, con `TRUSTED_PROXY_HOPS`); falta medir en Render cuántos saltos tiene `X-Forwarded-For` (1.4).
- **Recuperación de contraseña.** Siempre el mismo mensaje, exista o no la cuenta. El enlace se arma con `PUBLIC_BASE_URL`, nunca con la cabecera `Host` de la petición, y el token va tras `#` (`/restablecer-contrasena#token=...`) para que no llegue al servidor ni a los registros. En la base solo se guarda su hash; sirve una vez y caduca en 1 h. Hasta conectar Resend, el enlace solo se muestra en la consola en local (modo debug); en producción nunca se escribe en los registros. Cambiar la contraseña no inicia sesión.
- En producción, `FLASK_DEBUG=0`: la consola de depuración de Werkzeug permite ejecutar código en el servidor.
- Sin CORS: el frontend y la API comparten dirección. En desarrollo, Vite reenvía `/api` a Flask (puerto 3001) con un proxy. El frontend usa siempre rutas relativas `/api`, nunca una URL completa del backend.
- **Fotos (`images.py`).** Pillow abre el contenido real, no la extensión ni el `Content-Type`: solo JPEG, PNG y WebP, sin animación, hasta 10 MB y 25 MP (límites del plan Free de Cloudinary); dañada o cortada, se rechaza. Flask corta antes con `MAX_CONTENT_LENGTH` (413 "La foto pesa más de 10 MB."). Antes de subir se endereza según EXIF, se reduce a 2400 px por el lado largo y se vuelve a guardar sin EXIF, XMP ni comentarios (nada de GPS ni modelo de cámara), conservando el perfil de color: el original en Cloudinary es público si alguien quita la transformación de la URL. La llave (`CLOUDINARY_URL`) solo va en `.env` y en Render.
- Datos personales: guarda solo los necesarios. Hay un aviso de privacidad que cumplir (LFPDPPP). No cargues fuentes, scripts ni otros recursos de terceros que reciban la IP de las visitantes sin necesidad (Mercado Pago sí es necesario); si hace falta uno, pregunta.
- **HTML que arma el servidor (`seo.py`).** Todo dato de la base que va al HTML pasa por `markupsafe.escape`; en el JSON-LD, `<`, `>` y `&` van como `<`, `>` y `&` (probado con un producto llamado `</title><script>alert(1)</script>`). `index.html` nunca se entrega sin pasar por `seo.py`. Los enlaces absolutos salen solo de `PUBLIC_BASE_URL`, nunca de la cabecera `Host`.
- Si ves un riesgo de seguridad mientras trabajas en otra cosa, avísame aunque no lo haya pedido.

## Comandos
- Instalar backend: `pipenv install`
- Aplicar migraciones: `pipenv run upgrade`
- Generar una migración tras cambiar modelos: `pipenv run migrate -m "mensaje sin acentos"`
- Arrancar backend (puerto 3001): `pipenv run start`
- Crear una cuenta de administración (pide la contraseña sin mostrarla): `pipenv run flask create-admin`
- Comprobar en qué migración está la base: `pipenv run flask db current`
- Cargar datos de ejemplo en local (5 categorías, 17 productos con SKU `MUESTRA-` sin fotos y 2 paqueterías "(provisional)" de 150.00 y 250.00; no duplica): `pipenv run flask seed-sample`. Se niega a ejecutarse sin modo debug o con una base que no esté en localhost; nunca en Render.
- Instalar frontend: `npm install`
- Arrancar frontend: `npm run start`
- Compilar el frontend (lo que sirve Flask): `npm run build`
- Probar lo que entrega Flask (títulos, 404, robots y sitemap): `npm run build`, arrancar el backend y abrir `http://127.0.0.1:3001`. Desde PowerShell, con `curl.exe -i`, no con `curl`.
